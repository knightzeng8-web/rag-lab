# 多跳与 Agentic RAG：查询改写、证据聚合与自我纠错

单轮 RAG 把"检索一次"当作充分条件，但真实业务问题经常需要把多篇文档的事实串起来：先确定实体，再用该实体去查另一个属性。这类问题（例如"混合检索里 RRF 的默认常数是多少，它在评测上通常怎么验证收益"）无法靠一次向量检索覆盖，因为问题的最终答案在第二跳文档里，而第二跳的查询词只有在读完第一跳之后才能构造出来。多跳 RAG（Multi-hop RAG）与 Agentic RAG 就是为这类场景设计的迭代式检索框架。

## 一、Query Rewriting：把用户问题变成可检索的查询

用户问题与文档表述之间存在语义鸿沟，改写是第一道桥：

- **查询改写（Query Rewriting）**：用 LLM 把口语化问题改写成含关键词的检索式，同时去掉指代与礼貌用语。典型收益是 Recall@5 提升若干个百分点，代价是一次额外的 LLM 调用（延迟分解里通常记在 `rewrite` 阶段，量级 3～10ms 起，视模型而定）。
- **HyDE（Hypothetical Document Embeddings）**：先让模型生成一段"假想答案文档"，再对该文档编码去检索。原理是"答案与答案"的向量距离小于"问题与答案"，在缺少标注的领域文档上尤其有效；风险是假想文档可能引入错误事实，因此要求模型不要编造具体数值，最好配一轮验证。
- **查询分解（Query Decomposition）**：把复合问题拆成子问题列表，逐个检索后再聚合。例如"两者差别 + 各自参数"应拆成"是什么"与"参数取值"两支。
- **查询扩展与同义改写**：为同一问题生成多路改写并做多路召回，再用 RRF 融合（与混合检索用的是同一套融合算子）。

## 二、迭代检索：多跳的骨架

多跳的标准控制流是一个循环：

1. **检索**：用当前查询在混合检索器（向量 + BM25，RRF $k=60$）上取 top_k 候选；
2. **重排与筛选**：Cross-Encoder 精排，取出高置信片段；
3. **读证据、判断是否充分**：若信息不足，则基于已读内容构造下一跳查询（把"它/该参数"替换为具体实体名）；
4. **证据聚合**：把各跳片段合并，做去重、去矛盾与顺序重排；
5. **生成与引用**：以聚合后的证据为上下文作答，并保留每个断言的 `chunk_id` 出处。

关键工程约束：

- **跳数上限**：通常设 2～4 跳，超过后边际收益急剧下降而误差累积上升。
- **误差累积**：第一跳召回错误会让后续查询全部跑偏，因此每一跳都应保留"回到原始问题重检索"的退路。
- **上下文预算**：多跳证据总量易超出窗口，需要摘要压缩或按相关性截断，否则触发"迷失在中间"。
- **循环终止**：必须有显式的终止条件（证据充分 / 达到跳数 / 连续两跳无新增实体），否则 Agent 会空转。

## 三、Agentic RAG：把检索当作工具来调度

Agentic RAG 把检索器、计算器、SQL 查询、网页搜索都注册为工具，由模型自主决定调用哪一件、调用几次。相对固定流水线，它多了三项能力：

- **路由（Routing）**：先判断问题该走向量库、关键词库还是别的数据源，避免对所有查询套同一套链路。
- **自我纠错（Self-Correction）**：生成后自我检查引用是否支撑断言；不支持则重新检索或直接拒答。代表工作包括 Self-RAG（用反思标记决定是否需要检索、检索结果是否相关、答案是否被支持）与 CRAG（用一个轻量评估器给检索结果打"正确/模糊/错误"三档，错误时触发改写或外部搜索）。
- **工具组合**：多跳 + 计算 + 结构化查询的混合任务，单靠文本检索无法完成。

代价也很直接：token 消耗与延迟成倍增长，轨迹不可复现，评测难度上升（需要评"过程"而不仅是"结果"）。

## 四、评测多跳：只看最终答案是不够的

多跳评测需要同时报告：

1. **检索层**：每一跳的 Recall@5 / nDCG@10，以及**是否覆盖全部 gold 文档**（例如某题需要同时命中 `03-hybrid-retrieval` 与 `04-rerank-and-eval`，只命中其一就不算完整证据）。
2. **聚合层**：证据去重率、矛盾检出率。
3. **生成层**：答案正确率、引用准确率（多跳场景下引用错位更常见）、**拒答正确率**（对不可回答的问题必须拒答而不是硬答）。
4. **效率**：跳数分布、平均工具调用次数、端到端 P95 延迟。

一个典型的诊断模式是：多跳题的最终答案对了，但第二跳的 Recall 很低——说明模型靠参数化记忆补上了缺失证据，这在评测集内看不出问题，上线后遇到知识截止或私有语料就会失效。因此多跳系统必须逐跳审计证据，而不能只看最终输出。

## 五、何时不要上多跳

如果评测集里 80% 以上的问题都能被单个块回答，引入多跳只会抬高延迟与不确定性。稳妥的演进路径是：先把单跳链路做扎实（结构感知分块 512/128、混合召回 + RRF、Cross-Encoder 重排、引用准确率对齐），再用评测数据判断"可回答但未命中"的题目里有多少属于多跳缺失，最后才引入迭代检索——并且始终保留一条"低置信时直接拒答"的兜底路径。
